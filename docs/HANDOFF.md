## 3. Run and verify

```bash
python3 scripts/bootstrap_env.py http://localhost:8187
docker compose up --build -d     # gateway on :8187: / -> web, /api/ -> api, /ws/ -> api
```

- **API container startup:** it runs `alembic upgrade head && python -m app.seed && uvicorn` with 2 workers. The Celery worker runs with concurrency 2, and `beat` is a separate service.
- **Development login:** any phone number with code `00`. This only works while `SMS_PROVIDER=console`; the real codes are printed in `docker compose logs worker`. The bootstrap admin phone in `.env` opens `/admin`.

**Checks** (run before pushing):

```bash
cd services/api && pip install -r requirements-dev.txt && ruff check . && pytest
cd apps/web && npm ci && npm run typecheck && npm run build
cd apps/mobile && flutter analyze && flutter test
```

- **API tests run on SQLite and fakeredis** (`tests/conftest.py`), never on Postgres. So PostGIS-only paths are not covered by CI: `ST_DistanceSphere` in `GET /admin/drivers`, Geometry columns, and the asyncpg `statement_timeout`.
- **Web CI only typechecks and builds.** The one web unit test file runs by hand: `node --experimental-strip-types --test src/lib/googlePlaces.test.ts`.

**CI** (`.github/workflows`):

| Workflow | Runs automatically on push to | Manual run |
|---|---|---|
| `api-tests.yml` | `main`, `claude/**` (changes under `services/api`) | yes |

**Deploying:** merging to `main` does not deploy anything. The server has to pull `main` and run `docker compose up --build -d`. Mobile changes reach phones only through new builds (CI artifacts).

## 4. Contracts the code relies on

Break one of these only on purpose, and change both clients together.

### Auth and sessions

- **OTP request:** `POST /auth/otp/request` is rate-limited to 3 per phone and 15 per IP per 10 minutes, with a 60 s cooldown. The code is stored hashed in Redis for 5 minutes and deleted after 5 wrong attempts.
- **OTP verify:** `POST /auth/otp/verify` creates the user if new. It returns tokens in the body *and* sets cookies.
- **Access token:** a JWT valid for 15 minutes, in cookie `ag_access` (path `/`, max-age 900).
- **Refresh token:** random, valid for 30 days, stored hashed in `refresh_sessions`, in cookie `ag_refresh` (path `/api/auth`).
- **Refresh rotation:** `POST /auth/refresh` issues a new pair. The old refresh token stays valid for 30 s (`REFRESH_GRACE`) so parallel tabs and retries don't log the user out, then it dies.
- **Web vs mobile auth:** the web uses only the httpOnly cookies. Mobile sends `Authorization: Bearer` and passes the refresh token in the request body.
- **Renewal in both clients:** on a 401 with `SESSION_EXPIRED` or `LOGIN_REQUIRED`, they run one shared refresh, then retry once.
  - Web: `lib/api.ts`. This includes `/auth/me` and excludes only `/auth/otp/*` and `/auth/refresh`.
  - Mobile: `core/api_client.dart`.
  - A refresh that fails on the network keeps the session. Only a server rejection logs the user out.
- **Phone-first home page:** `app/page.tsx` renders `PhoneLogin` immediately. A background `/auth/me` sends an already signed-in customer straight to `CustomerFlow`, which also checks the session itself in `boot()`.
- **Dev code `00`:** accepted only while `SMS_PROVIDER=console`. `GET /config` returns `dev_otp`, and both clients show the hint and accept `00` only when it is true.

### Quote → order

- **Quote:** `POST /quotes {pickup, dropoff, loaders}` returns the route, a price for each active service and a `quote_token`. The token is a JWT (`kind=quote`, valid 300 s) that signs the route hash, the totals, the route and each service's price breakdown.
- **Order:** `POST /orders` needs an `Idempotency-Key` header, `quote_token` and `expected_total`. The server charges the signed breakdown and does not route again.
- **Order errors:**
  - Any mismatch, an expired token or a service switched off returns **409 `QUOTE_CHANGED`**. Clients then re-quote; it must never be a 401.
  - The same key with a different body returns 409 `IDEMPOTENCY_CONFLICT`.
  - A second active order returns 409 `ACTIVE_ORDER_EXISTS`, and the clients resume the existing order.
- **Pricing:** only `pricing.calculate_price()` computes prices.
  - The night surcharge uses the Asia/Ulaanbaatar hour, and the total is rounded to the nearest 500₮.
  - The full breakdown is stored on the order.
  - `floor_rate` exists in the settings but is not used yet.

### Order lifecycle and realtime

- **Statuses:** the allowed transitions are `TRANSITIONS` in `pricing.py`. Customers can cancel in `CUSTOMER_CANCEL_STATUSES` (default: pending, assigned, driver_arriving, arrived). There are no cancellation fees yet.
- **`orders.record()`:** every status change goes through it, which writes an `order_events` row and an `outbox` row in the same transaction.
- **Completion:** `completed` requires a paid payment (`PAYMENT_REQUIRED`). `delivered` completes the order straight away if it is already paid.
- **Outbox:**
  - Beat runs `achaago.flush_outbox` every 2 s. Rows are locked with `FOR UPDATE SKIP LOCKED`.
  - Each row is delivered on its own: a Redis publish to `order:{id}`, an SMS or an FCM push.
  - Failures retry with backoff (5 s doubling up to 10 minutes). After 8 attempts the row is dropped and logged at ERROR, which triggers a Telegram alert when alerts are on.
  - Periodic tasks expire instead of piling up while the worker is down.
  - An hourly cleanup deletes delivered outbox rows older than 7 days and expired refresh sessions.
- **Customer SMS:** sent when a driver is assigned (driver name, plate and the `/t/{token}` link) and when the driver arrives.
- **Dispatch timeout:** pending orders become `no_driver_found` after `DISPATCH_TIMEOUT_MINUTES` (default 30), checked every 60 s.
- **WebSockets:**
  - `/ws/orders/{id}` authenticates with the `ag_access` cookie, or with a first message `{"token": ...}` within 10 s, which mobile uses.
  - `/ws/tracking/{token}` is public and returns limited fields.
  - The server sends `{"type": "snapshot", "order": ...}` on every event and at least every 20 s.
  - Close codes:
    - 4401 when the access token expires, after 15 minutes on tracking sockets, or on an error.
    - 4403 for a foreign `Origin`.
  - The web clients reconnect, and the customer socket renews the session on 4401. Mobile polls every 5 s alongside its socket and does not reconnect the socket.
- **Driver location:**
  - `POST /driver/location` is limited to 40 per minute.
  - It writes Postgres (`last_lat`, `last_lng`, PostGIS `last_point`) and the Redis GEO set `drivers:geo`, then publishes a location event to the driver's active orders.
  - A location counts as fresh for 90 s.

### Dispatch (manual)

- **Picking a driver:** `GET /admin/drivers?order_id=` lists drivers, eligible ones first, then by PostGIS distance to the pickup.
- **Assigning:** `POST /admin/orders/{id}/assign` checks that the driver is approved, online, has a fresh location and is not busy, and that their vehicle's service matches the order.
- **Driver side:** `GET /driver/offers` returns only orders already assigned to that driver. `accept` moves the order from `assigned` to `driver_arriving`.
- **Automatic matching** must replace the assignment step in the backend only, leaving the customer UI unchanged (AGENTS.md §2).

### Payments

- **QPay invoice:** created on demand (`POST /orders/{id}/qpay-invoice`), with a callback URL that carries a secret unique to that payment.
- **QPay webhook:** `/payments/qpay/webhook` is only a signal. The server re-checks with QPay, requires the amount to match, and handles repeats idempotently. Customers can also poll `POST /orders/{id}/check-payment`.
- **QPay token:** cached in Redis until shortly before expiry. QPay sends `expires_in` as a Unix time.
- **Cash:** after delivery, the driver (or staff) calls `POST /orders/{id}/cash-received`, which marks the payment paid and completes the order.

### Errors, time limits, security

- **Errors:** responses are `{"detail": "CODE"}`, and clients map codes to Mongolian in `apps/web/src/lib/messages.ts` and `apps/mobile/lib/l10n/errors_mn.dart`. **Add every new code to both.** Unhandled errors return 500 `{"detail": "SERVER_ERROR", "request_id": ...}`.
- **Request IDs:** every response carries `X-Request-ID` (nginx passes its own). Requests slower than 2 s are logged with their ID.
- **Time limits line up:**
  - Web reads 15 s, writes 30 s.
  - Mobile 15 s and 30 s.
  - nginx 30 s.
  - Postgres `statement_timeout` 25 s.
  - The web retries a failed GET once, for network errors only, not after a timeout.
- **Origin guard:** a non-GET request that carries session cookies must send `Origin` equal to `PUBLIC_URL`, or it gets 403 `ORIGIN_NOT_ALLOWED`.
- **Server-side authority:** prices and status changes are always decided by the server (AGENTS.md §12).

## 5. Production setup

`README.md` → "Production" has the steps. In short:

- **Startup check:** `APP_ENV=production` refuses to start until `PUBLIC_URL` is HTTPS and real SMS, Google Maps and QPay providers are configured (`config.py`).
- **HTTPS:** set `DOMAIN`, `PUBLIC_URL=https://…` and `GATEWAY_BIND=127.0.0.1`, then run `docker compose --profile https up -d`. Caddy gets and renews the Let's Encrypt certificate. Cookies become `Secure` automatically.
- **SMS:** `SMS_PROVIDER=http` with `SMS_HTTP_*` templates that fit any HTTP gateway. No provider has been chosen yet.
- **Backups:** the `backup` service writes a daily `pg_dump` to `.data/backups/` and keeps `BACKUP_KEEP_DAYS` days. The folder must also be copied off the server.
- **Alerts:** `ALERT_PROVIDER=telegram` with a bot token and chat ID. It reports unhandled errors, failed tasks, dropped messages and a stopped worker, at most once per 10 minutes per problem.
- **Health checks:** `/api/health` checks the API and database (liveness). `/api/health/full` checks the database, Redis and the worker heartbeat, and returns 503 if any is down; point an uptime monitor at it.
- **Logs:** every service rotates its Docker logs at 10 MB × 5 files.

## 8. Gotchas

- **iOS local builds:** with Xcode 26.0, `flutter run` and `flutter build ios` from the CLI fail at "Run Prepare Flutter Framework Script" (exit 255). Run `flutter build ios --config-only --dart-define=…`, then build and run from the Xcode GUI. CI builds are fine.
- **API keys are never committed, and the repository is public.**
  - CI takes them from the repository secrets.
  - Locally, `GOOGLE_MAPS_API_KEY_IOS=… tool/prepare_ios.sh` writes the key into the gitignored `ios/Runner/AppDelegate.swift`, and `prepare_android.sh` does the same for the Android manifest.
  - The web key is `NEXT_PUBLIC_GOOGLE_MAPS_API_KEY` in `.env`.
  - The signing keystore lives only in a secret.
- **Plain-HTTP limits:** geolocation, `crypto.randomUUID`, service workers and `Secure` cookies all need HTTPS. Keep the `uuid()` fallback in `lib/api.ts` until the site is HTTPS-only.
- **Strings:** all user-facing text is Mongolian, kept in `customerCopy.ts` / `messages.ts` (web) and `strings.dart` / `errors_mn.dart` (mobile). Code, comments and docs are in English.
